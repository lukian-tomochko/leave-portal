# 0003. Секретний ключ Supabase й admin-клієнт лише в серверному коді

- Статус: прийнято
- Дата: 2026-10-25
- AC: AC-LEAVE-14, AC-BALANCE-12, AC-BALANCE-13

## Контекст

Публічний ключ Supabase (`sb_publishable_…`) лежить у JS-бандлі, тож будь-хто може надіслати запит прямо в базу. Дані
працівників захищають лише RLS і явні GRANT: AC-LEAVE-14 (працівник бачить лише власні записи), AC-BALANCE-12 й
AC-BALANCE-13 (баланси чужих працівників недоступні тим, хто не керує їхніми посадами, і самим працівникам один одного).
Секретний ключ (`sb_secret_…`) обходить RLS: якщо він потрапить у браузер, у Preview-деплой чи в код сторінки, усі ці AC
перестають діяти. Зараз застосунок admin-клієнта не має й не потребує: зріз 1 працює лише з публічним ключем і сесією
користувача, а тестових користувачів створює локальний скрипт `scripts/create-demo-users.mjs`. Рішення фіксує правило наперед,
поки адмін-дії (створення користувачів, ролі, календар) ще не з'явились.

## Рішення

- Сьогодні `SUPABASE_SECRET_KEY` читається лише в `scripts/` (локально, поза `src/`), як вимагає розділ «Секрети»
  в `AGENTS.md`. Змінних `NEXT_PUBLIC_*SECRET*` чи `NEXT_PUBLIC_*SERVICE_ROLE*` немає.
- Читати ключ у `src/lib/supabase/admin.ts` дозволено лише після нового ADR **і** зміни правила в `AGENTS.md`. Скрипт
  `check:boundary` уже робить `admin.ts` єдиним винятком у `src/`, але без цієї зміни файл не створюємо. Коли він
  з'явиться, він починається з `import "server-only"`.
- Admin-клієнт можна імпортувати лише у `actions.ts`, `route.ts` або файли з `"use server"`, ніколи у файли з `"use client"`. Перевірка ролі
  (`getClaims()` і роль із `profiles`) стоїть **до** admin-клієнта; кожна така дія вважається публічним POST-ендпойнтом.
- У Vercel ключа немає: лише `NEXT_PUBLIC_SUPABASE_URL` і `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. Якщо зріз справді
  викличе Admin API, ключ додаємо лише в Production і заміняємо цей ADR.
- Привілейовану дію, якій можна обійтись без обходу RLS, робимо функцією бази з перевіркою ролі всередині.

## Розглянуті варіанти

- **Admin-клієнт у спільному `lib`-модулі, який імпортують звідусіль.** Зручно, але один імпорт у файл із
  `"use client"` віддає ключ у бандл, а виклик із допоміжного модуля обходить перевірку ролі в самій дії. Відхилено.
- **Ключ у Vercel для всіх середовищ «про всяк випадок».** Preview-адреси відкриті всім за посиланням (Require Log In
  вимкнено, щоб PM бачив деплої), тож будь-який preview із помилкою обходив би RLS. Відхилено.
- **Покладатися лише на рев'ю.** Агент може «спростити» ізоляцію й імпортувати admin-клієнт у клієнтський компонент;
  рецензент може пропустити. Відхилено на користь перевірки в CI.

## Наслідки

- Поки admin-клієнта немає, правило нічого не блокує, але вже ловить спробу його додати неправильно.
- Скрипт не бачить, чи є перевірка ролі перед admin-клієнтом: це тест на кожен відмовний AC і рев'ю.
- Для адмін-зрізів потрібен окремий ADR: чи функція бази, чи Server Action з admin-клієнтом.

## Як перевіряємо

- **`npm run check:boundary`**, job «Секретний ключ лише на сервері» в `.github/workflows/architecture.yml`
  (`scripts/check-server-boundary.mjs`): завершується помилкою, якщо код у `src/` читає ключ поза `admin.ts` або імпортує admin-клієнт із
  `"use client"` чи з допоміжного модуля (також відносним шляхом `../supabase/admin`), або є `NEXT_PUBLIC_…SECRET…`.
  Скрипт обходить лише `src/`: `scripts/create-demo-users.mjs`, який читає ключ, у CI не перевіряється.
- **Доказ, що правило ловить порушення:** на навмисних порушеннях скрипт виходить із кодом 1 і друкує 5 порушень
  (вивід — в описі PR, який додав цей ADR); без порушень друкує `OK`.
- **Правило для агента:** `AGENTS.md`, розділи «Секрети» й «Межі».
